## 1. Getty rules: one rulebook

The same rule is written differently in different places:

| Rule | `getty/metadata-rules.md` + metadata tool prompt | `getty-keyword-lessons.md` |
|---|---|---|
| Dateline | `Kensington, London — 7 March 2026:` (text says "en dash" but shows an em dash, then a colon) | `London, England, United Kingdom – 14 February 2026.` (en dash, full stop) |
| Description | Two sentences, ≥ 120 words | Two paragraphs |
| Keyword count | Exactly 50 | 40–55; below 30 is under-tagged; 66 is the highest seen |
| `Colour Image`, `Horizontal` | Exclude: handled by other fields | Core keywords: include (`Color Image`) |
| Location keywords | Exclude London, England, UK, Europe | Include geography compounds (`London - England`, `Kensington And Chelsea`) |
| Time of day | `Daytime` | `Day` |
| Title length | 60 characters | DeepMeta limit is 63 |

The keyword-lessons file is the later one and is based on sales evidence, so it probably reflects what you do now. But the metadata tool still sends the older rules to Claude, and anyone reading `metadata-rules.md` gets the older version.

**Recommendation:** make the Getty project's current instructions canonical. Copy them into `getty/metadata-rules.md`, turn the older file into a short "superseded" note, and have every tool (prompt, project, DeepMeta checklist) point to that one file. Keyword choices can't be edited after submission, so a contradiction here costs sales permanently.

**Decision for you:** which dateline and which keyword policy is current? See [decisions](backlog.md#decisions-for-you).

## 3. On Foot blog

### 3.1 The notes → Getty link is missing (biggest opportunity)

Getty's sentence 2 ("specific historical, geographical or architectural context… named architects, dates, borough history") is what the walk guide told you. The blog Action was built to save that context in `_data/<slug>.json` (stops, dates, historical figures, `getty_keywords`, `suggested_caption_prefix`). In practice:

- `_notes/` is empty. Posts are being uploaded already finished, so the sidecar step never runs.
- The two sidecars that exist (`kap-karoso-2025`, `krakow-jewish-quarter-2026`) contain only the homepage card data.
- Nothing in the Getty pipeline reads `_data/`.

**Recommendation:** for each walk you photograph, produce a **"shoot context" pack**: the stops, dates, named people, and the right Getty geography compounds. Paste it into the Getty project's "Shoot Context" field. Two ways to get there:

- **(a)** Add a manual Action that builds the pack from the finished post. It needs no notes and uses the Claude API key already in place.
- **(b)** Ask the Getty project to read the post's URL.

(a) is repeatable and keeps a file per walk; I can build it. This is the single largest synergy across your projects: better sentence-2 context means better Getty search ranking, on the walks you're already shooting.

Each is either a photo you could submit (Sydenham and Gunnersbury are this month's), or one already on Getty whose link is missing. The list doubles as a **submission queue**. I can add a check that lists them on every build.

### 3.3 Photo weight and the 1 GB ceiling

- `images/` is 438 MB: 283 MB of 1600px copies (avg 840 KB each), 109 MB of 1200px and 55 MB of 800px. The git history is 471 MB.
- GitHub Pages sites are capped at 1 GB. At about 8.6 MB of photos per post, you'll reach it at around 110 posts.
- A free 1600px, 840 KB copy of an editorial picture is also *more* than a blog reader needs, and close to what a web buyer would license.

**Recommendation:** for new posts, make 1200px the largest size served (the 1600px copy can stay on the Mac). This roughly halves storage per photo, and the Getty page becomes the only way to get a bigger file. Keep the existing posts as they are. Rewriting git history to shrink the repo isn't worth the risk.

## 4. London List and "Where next?"

This is already the place where the three strands meet: Getty shoots (folders and Lightroom times), On Foot posts and DeepMeta sales come together to suggest the next outing. It's well built. Improvements, in order of Getty value:

1. **Subject, not just area.** Sales are scored per area (`fruit`), but what sells is a subject: flags, landmarks, niche produce, per your RPD table. A small subject map (subject → sales score, and how much Getty already has of it) would let "Where next?" say "this has 3 flags you haven't shot". It links to your "subject scarcity beats keyword density" rule.
2. **Timeliness.** Editorial sales favour events: Open House (September), the London Festival of Architecture (June), Christmas markets, protests, openings, demolitions. An events file (date, place, subject) weighted in the score would help.
3. **Refreshing the planner takes four manual steps** (copy the catalogue, extract times, gather sales, build, then load on the phone). Combine them into one `refresh.command` you double-click, and put a "planner is N days old" warning in the app.
4. The blog side could read the public `sitemap.xml`/`feed.xml` instead of a local copy of the repo, so posts appear without a local `git pull`.
